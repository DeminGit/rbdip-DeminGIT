## ЛР2

Добавлены характеризационные тесты цены, таблица customers, внешние ключи
orders.customer_id / order_items.product_id и перенос старых данных в V2.
Клиенты с одинаковыми именем, адресом и телефоном переиспользуются атомарно.
В V1 идентификатор купленного товара отсутствует: для совпадающих имени и цены
выбирается минимальный существующий ID; отсутствующие исторические товары
сохраняются отдельными строками products.

Совместимость со старым приложением обеспечивают триггеры. Старые поля пока
сохранены: schema-гейт будет закрыт contract-миграцией ЛР3. Удаление этих полей
в V2 противоречило бы неизменяемому тесту ЛР3, который читает customer_full_name
в orders на всех версиях до последней. V2 после публикации не переписывается.

Исправлена обнаруженная ошибка ЛР1: PricingCalculator зарегистрирован как
Spring-компонент, необходимый конструктору OrderService.

## ЛР3

V3 добавляет first_name/last_name и двусторонний триггер совместимости в customers,
переносит имена без потери составных фамилий; V4 отдельно проверяет ограничения.
Приложение читает новые поля, но сохраняет прежний JSON customerFullName.
V5 удаляет старые колонки и триггеры. История V1/V2 неизменна.

Порядок обновления работающего сервиса:

1. Пока работает версия ЛР2, накатить V3/V4 отдельным Flyway runner или задать
   `SPRING_FLYWAY_TARGET=4` новой версии перед её запуском.
2. Постепенно заменить все экземпляры приложением ЛР3, читающим новые поля.
   Старые экземпляры совместимы с V3/V4 через триггеры.
3. После отключения всех старых экземпляров разрешить V5 (снять target).
   Автоматический запуск до latest подходит для новой базы, но не заменяет
   этот порядок при rolling deployment.

Собственный HTTP-тест запускает приложение на V3, одновременно создаёт/читает
заказы и накатывает V4/V5; проверяет завершение потоков, реальные ответы и данные.
Эталонный JDBC-тест отдельно проверяет старые чтения во время V2–V4.
Для больших production-таблиц backfill и создание индексов нужно дробить;
учебная проверка подтверждает доступность только на своём объёме и нагрузке.

## ЛР4

GET /orders использует один JOIN FETCH для клиентов, позиций и товаров,
формирует прежний JSON внутри read-only транзакции и не теряет заказы без позиций.
Модуль review зависит от публичного purchase.PurchaseHistory; реализация в order
проверяет конкретного автора и товар одним EXISTS. Как и раньше, отсутствие
покупки не запрещает отзыв; результат проверки доступен в диагностическом логе.
Внутренние репозитории order больше не доступны модулю review через зависимости.

При повторной нагрузке выявлена ошибка cached plan must not change result type:
RETURNING * меняет форму результата после DROP COLUMN. Запрос разрешения клиента
теперь перечисляет поля явно, а HTTP-тест предварительно прогревает prepared
statements с prepareThreshold=1 перед contract-миграцией.

Нагрузочный прогон также обнаружил deadlock при разном порядке блокировок DDL
и записи заказа. Callback beforeEachMigrate__lock_contract.sql перед V5 получает
все блокировки через NOWAIT, освобождая частично полученные блокировки при
конфликте и повторяя попытку до 5 секунд. Запросы приложения продолжаются,
а при невозможности получить блокировки откладывается миграция. Это дополнение
не меняет checksum уже опубликованных V1–V5.

## ЛР5

Подключён pitest-junit5-plugin 1.2.2, совместимый с PIT 1.17.3:
без него исходный PIT не запускал JUnit 5 тесты. Добавлены сценарии сочетания
скидок, границ после купонов и округления после суммирования строк.
Пороги 60% покрытия/мутаций и 15 нарушений стиля сохранены.

Maven больше не игнорирует падения тестов и недостаточное покрытие.
CI начинает с clean verify, сохраняет отчёты даже при ошибке и завершается
обязательной проверкой check_results.py. Исходный write_score.py не меняется;
дополнительная проверка учитывает реальные нарушения PMD с XML namespace,
отсутствующие/пустые JUnit-отчёты, пропуски, ошибки и неполные PIT-результаты.

## Как проверять

Нужны Java 21, Maven, Python 3 и работающий Docker с Linux-контейнерами.

```sh
mvn clean verify
mvn org.pitest:pitest-maven:mutationCoverage
python scripts/write_score.py
python scripts/check_results.py
```

Смотрите все `gates.*.passed` и `score = 100` в score.json, а также отчёты
JUnit в target/surefire-reports (ни ошибок, ни пропущенных тестов), Checkstyle,
PMD, JaCoCo и PIT. В исходной конфигурации BUILD SUCCESS и зелёный Actions
не гарантируют прохождение тестов: ошибки допускаются настройками Maven/CI.
В GitHub откройте Actions → запуск для нужного SHA → артефакты score и reports.
